Kurze, allgemein verwendbare Snippets für WPF mit MVVM.

== Projektstruktur

----
MyApp/
├── MyApp.csproj        ← WinExe, net10.0-windows, UseWPF
├── App.xaml            ← StartupUri + globale Ressourcen
├── Tools/              ← MVVM-Bausteine (PropertyChanged, Commands, Converter)
├── Models/             ← reine Daten/Logik, kein WPF
├── ViewModels/         ← Properties + Commands für die View
└── Views/              ← XAML-Fenster, Code-Behind nur InitializeComponent()
----

* *Model*: Daten und Logik, unabhängig vom UI.
* *ViewModel*: stellt Daten als Properties bereit und Aktionen als `ICommand`. Meldet Änderungen über `INotifyPropertyChanged`.
* *View*: nur XAML, mit dem ViewModel über `{Binding}` verbunden.
* Typische Gliederung im ViewModel: `#region Properties` → `#region Operations` → `#region Commands`.

=== csproj

[source,xml]
----
<OutputType>WinExe</OutputType>
<TargetFramework>net10.0-windows</TargetFramework>
<UseWPF>true</UseWPF>
----

* `WinExe`: GUI-Anwendung ohne Konsolenfenster.
* `-windows` + `UseWPF`: bindet WPF ein. Läuft nur unter Windows.

=== Startfenster in einem Unterordner

[source,xml]
----
<Application ... StartupUri="/Views/MainWindow.xaml">
----

* Nach dem Verschieben in `Views/` auch `x:Class="MyApp.Views.MainWindow"` und den Namespace in der `.xaml.cs` anpassen.

=== ViewModel als DataContext setzen

[source,xml]
----
<Window ... xmlns:vm="clr-namespace:MyApp.ViewModels">
    <Window.DataContext>
        <vm:MainWindowViewModel />
    </Window.DataContext>
----

* `xmlns:vm="clr-namespace:..."` macht einen C#-Namespace in XAML verfügbar.
* Der `DataContext` wird an alle Kind-Elemente vererbt, daher sucht `{Binding X}` die Property `X` im ViewModel.
* Das ViewModel braucht einen öffentlichen parameterlosen Konstruktor.

== Properties und Benachrichtigung

=== PropertyChanged auslösen

[source,csharp]
----
public event PropertyChangedEventHandler PropertyChanged;

protected void OnPropertyChanged([CallerMemberName] string name = null)
    => PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(name));
----

* Kern von `INotifyPropertyChanged`: teilt dem UI mit, dass sich eine Property geändert hat.
* `[CallerMemberName]` setzt den Property-Namen automatisch ein. Im Setter also ohne Argument aufrufen.
* Am besten in eine Basisklasse legen, von der alle ViewModels erben.

=== SetProperty-Helfer

[source,csharp]
----
protected bool SetProperty<T>(ref T field, T value, [CallerMemberName] string name = null)
{
    if (EqualityComparer<T>.Default.Equals(field, value)) return false;
    field = value;
    OnPropertyChanged(name);
    return true;
}
----

* Setzt das Feld und meldet die Änderung nur, wenn sich der Wert wirklich geändert hat.
* Gibt `true` zurück, wenn sich etwas geändert hat. So kann man im Setter weitere Schritte anhängen.

=== Bindbare Property

[source,csharp]
----
private string _name;
public string Name
{
    get => _name;
    set => SetProperty(ref _name, value);
}
----

* Standardmuster für jede Property, deren Änderung im UI sichtbar sein soll.

=== Abhängige / berechnete Property

[source,csharp]
----
public int Count
{
    get => _count;
    set
    {
        if (SetProperty(ref _count, value))
            OnPropertyChanged(nameof(IsEmpty));
    }
}

public bool IsEmpty => Count == 0;
----

* Berechnete Properties haben keinen Setter. Sie werden im Setter der Quelle mit `OnPropertyChanged(nameof(...))` mitgemeldet.

=== Listen

[source,csharp]
----
public ObservableCollection<Item> Items { get; } = new();

Items.Add(item);
Items.Remove(item);
Items.Clear();
----

* `ObservableCollection<T>` meldet `Add`/`Remove`/`Clear` automatisch an das UI. `List<T>` tut das nicht.
* Die Instanz nie ersetzen (nur `{ get; }`), sondern nur ihren Inhalt ändern.
* Ändert sich eine *Property eines Elements*, sieht man das nur, wenn die Elementklasse selbst `INotifyPropertyChanged` implementiert.

== Commands

=== CanExecuteChanged an den CommandManager hängen

[source,csharp]
----
public event EventHandler CanExecuteChanged
{
    add => CommandManager.RequerySuggested += value;
    remove => CommandManager.RequerySuggested -= value;
}
----

* Kernstück einer eigenen `ICommand`-Klasse (z. B. `DelegateCommand` / `RelayCommand`, die `Action` + `Func<bool>` speichert).
* WPF prüft `CanExecute` damit nach jeder Benutzereingabe automatisch neu.

=== Command im ViewModel anlegen

[source,csharp]
----
public ICommand SaveCommand { get; }

public MainWindowViewModel()
{
    SaveCommand = new DelegateCommand(Save, () => !string.IsNullOrEmpty(Name));
}
----

* Commands einmal im Konstruktor erzeugen, nicht bei jedem Lesen (`=> new ...`).
* Liefert die zweite Lambda `false`, wird der gebundene Button automatisch deaktiviert.

=== Command binden

[source,xml]
----
<Button Content="Speichern" Command="{Binding SaveCommand}" />
<Button Content="7" Command="{Binding InputCommand}" CommandParameter="7" />
----

* `CommandParameter` übergibt einen Wert an `Execute(object parameter)`. Aus XAML kommt ein `string`.
* So bedient ein einziger Command viele gleichartige Buttons.

=== CanExecute manuell neu prüfen

[source,csharp]
----
CommandManager.InvalidateRequerySuggested();
----

* Nötig, wenn sich der Zustand ohne Benutzereingabe ändert (Timer, async-Code).

=== Tastenkürzel

[source,xml]
----
<Window.InputBindings>
    <KeyBinding Key="Enter" Command="{Binding SubmitCommand}" />
    <KeyBinding Key="S" Modifiers="Control" Command="{Binding SaveCommand}" />
    <KeyBinding Key="D1" Command="{Binding InputCommand}" CommandParameter="1" />
</Window.InputBindings>
----

* Verknüpft Tasten mit denselben Commands, die auch die Buttons verwenden.
* Die Zifferntasten der oberen Reihe heißen `D0`–`D9`, die des Nummernblocks `NumPad0`–`NumPad9`.

== Layout

=== Grid

[source,xml]
----
<Grid>
    <Grid.RowDefinitions>
        <RowDefinition Height="Auto"/>
        <RowDefinition Height="*"/>
        <RowDefinition Height="2*"/>
        <RowDefinition Height="40"/>
    </Grid.RowDefinitions>
    <Grid.ColumnDefinitions>
        <ColumnDefinition/>
        <ColumnDefinition/>
    </Grid.ColumnDefinitions>

    <TextBox Grid.Row="0" Grid.ColumnSpan="2"/>
    <Button  Grid.Row="1" Grid.Column="1" Grid.RowSpan="2"/>
</Grid>
----

* `Auto` = so groß wie der Inhalt, `*` = restlicher Platz, `2*` = doppelter Anteil, Zahl = feste Pixel.
* `Grid.Row/Column` sind 0-basiert. `RowSpan/ColumnSpan` verbinden Zellen.
* Elemente in derselben Zelle liegen übereinander.

=== GridSplitter

[source,xml]
----
<GridSplitter Grid.Column="1" Width="5" HorizontalAlignment="Stretch"/>
----

* Der Benutzer kann benachbarte Spalten (oder Zeilen) per Ziehen in der Größe ändern. Am besten in eine eigene schmale Spalte legen.

=== StackPanel

[source,xml]
----
<StackPanel Orientation="Horizontal" Margin="0,2,0,0">
    <Label Content="Name" Width="100"/>
    <TextBox Width="150"/>
</StackPanel>
----

* Stapelt Elemente vertikal (Standard) oder horizontal. Gut für Label + Eingabe-Zeilen und Button-Leisten.
* Begrenzt die Größe der Kinder nicht, daher scrollt eine `ListBox` darin nie. Stattdessen eine Grid-Zeile mit `*` verwenden.

=== DockPanel

[source,xml]
----
<DockPanel LastChildFill="True">
    <Menu DockPanel.Dock="Top"/>
    <StatusBar DockPanel.Dock="Bottom"/>
    <ContentControl/>
</DockPanel>
----

* Dockt Elemente in der Reihenfolge ihrer Deklaration an die Ränder. Das letzte Element füllt den Rest.

=== WrapPanel / UniformGrid

[source,xml]
----
<WrapPanel ItemWidth="80"> ... </WrapPanel>
<UniformGrid Rows="3" Columns="3"> ... </UniformGrid>
----

* `WrapPanel`: bricht in die nächste Zeile um, wenn der Platz ausgeht.
* `UniformGrid`: alle Zellen gleich groß, wird zeilenweise befüllt, kein `Grid.Row` nötig.

=== Canvas

[source,xml]
----
<Canvas Background="White">
    <Ellipse Canvas.Left="50" Canvas.Top="20" Width="20" Height="20" Fill="Red"/>
    <Line X1="0" Y1="0" X2="100" Y2="100" Stroke="Black" StrokeThickness="2"/>
</Canvas>
----

* Absolute Positionierung mit `Canvas.Left/Top`. Zum Zeichnen und für freie Anordnung.
* Ohne `Background` empfängt der Canvas keine Mausklicks.

=== ScrollViewer

[source,xml]
----
<ScrollViewer HorizontalScrollBarVisibility="Auto" VerticalScrollBarVisibility="Auto">
    ...
</ScrollViewer>
----

* Zeigt Scrollbalken, wenn der Inhalt größer als der sichtbare Bereich ist.

=== Häufige Layout-Properties

* `Margin="links,oben,rechts,unten"`: Abstand nach außen. `Padding`: Abstand nach innen.
* `HorizontalAlignment` / `VerticalAlignment`: `Left|Center|Right|Stretch`.
* `HorizontalContentAlignment`: richtet den Inhalt innerhalb eines Controls aus.
* `MinWidth`, `MaxWidth`, `Width="Auto"`.

=== Element drehen

[source,xml]
----
<Polygon RenderTransformOrigin="0.5,0.5" ...>
    <Polygon.RenderTransform>
        <RotateTransform Angle="{Binding Angle}"/>
    </Polygon.RenderTransform>
</Polygon>
----

* `RenderTransformOrigin="0.5,0.5"` dreht um die Mitte statt um die linke obere Ecke.

== Data Binding

=== Grundsyntax

[source,xml]
----
<TextBox   Text="{Binding Name, UpdateSourceTrigger=PropertyChanged}"/>
<TextBlock Text="{Binding Count, StringFormat='Anzahl: {0}'}"/>
<TextBlock Text="{Binding Price, StringFormat={}{0:F2} €}"/>
<TextBlock Text="{Binding Selected.Name, FallbackValue='-'}"/>
----

* `{Binding Name}` liest `Name` aus dem `DataContext`. Verschachtelte Pfade wie `Selected.Name` funktionieren.
* `StringFormat` formatiert den Wert. `{}` maskiert einen Format-String, der mit `{` beginnt.
* `FallbackValue` wird angezeigt, wenn das Binding fehlschlägt.
* Bindings funktionieren nur mit öffentlichen *Properties*, nicht mit Feldern.

=== Mode und UpdateSourceTrigger

[source,xml]
----
<TextBox Text="{Binding Name, Mode=TwoWay, UpdateSourceTrigger=PropertyChanged}"/>
<TextBlock Text="{Binding Status, Mode=OneWay}"/>
----

* `OneWay`: Quelle → UI. `TwoWay`: beide Richtungen (Standard bei `TextBox.Text`, `IsChecked`, `Slider.Value`).
  `OneTime`: einmal lesen. `OneWayToSource`: nur UI → Quelle.
* `UpdateSourceTrigger=PropertyChanged` schreibt bei jedem Tastendruck zurück. Standard bei der TextBox ist `LostFocus`.

=== An ein anderes Control binden

[source,xml]
----
<Slider x:Name="slider" Minimum="0" Maximum="100"/>
<TextBlock Text="{Binding ElementName=slider, Path=Value}"/>
----

* `ElementName` bindet an ein benanntes Element statt an den DataContext.

=== Aus einem Template an das ViewModel des Fensters binden

[source,xml]
----
<Button Command="{Binding DataContext.DeleteCommand,
                  RelativeSource={RelativeSource AncestorType=Window}}"
        CommandParameter="{Binding}"/>
----

* In einem `DataTemplate` ist der DataContext das *Element*, nicht das ViewModel.
* `RelativeSource AncestorType=Window` greift auf den DataContext des Fensters zu. `{Binding}` übergibt das ganze Element.

=== Auswahl / Master-Detail

[source,xml]
----
<ListBox ItemsSource="{Binding Items}" SelectedItem="{Binding SelectedItem}" DisplayMemberPath="Name"/>
<TextBox Text="{Binding SelectedItem.Name}"/>
----

* `SelectedItem` bindet TwoWay an eine Property im ViewModel.
* `DisplayMemberPath` zeigt eine Property an, ohne ein Template zu schreiben.

== Listen und Templates

=== ItemsControl mit DataTemplate

[source,xml]
----
<ItemsControl ItemsSource="{Binding Items}">
    <ItemsControl.ItemTemplate>
        <DataTemplate>
            <StackPanel Orientation="Horizontal">
                <TextBlock Text="{Binding Name}"/>
                <TextBlock Text="{Binding Value}" Margin="10,0,0,0"/>
            </StackPanel>
        </DataTemplate>
    </ItemsControl.ItemTemplate>
</ItemsControl>
----

* `DataTemplate` legt fest, wie ein Element aussieht. Die Bindings darin beziehen sich auf das Element.
* `ItemsControl` hat weder Auswahl noch Scrolling. `ListBox` ergänzt Auswahl, `ListView` ergänzt Spalten.

=== Anordnung ändern (ItemsPanel)

[source,xml]
----
<ItemsControl.ItemsPanel>
    <ItemsPanelTemplate>
        <UniformGrid Columns="3"/>   <!-- oder WrapPanel, Canvas, StackPanel Orientation="Horizontal" -->
    </ItemsPanelTemplate>
</ItemsControl.ItemsPanel>
----

* Ersetzt das Standard-Panel (vertikales StackPanel). Damit werden Listen zu Rastern, Spielfeldern oder Zeichenflächen.

=== Position im Canvas aus Daten (ItemContainerStyle)

[source,xml]
----
<ItemsControl.ItemContainerStyle>
    <Style TargetType="ContentPresenter">
        <Setter Property="Canvas.Left" Value="{Binding X}"/>
        <Setter Property="Canvas.Top"  Value="{Binding Y}"/>
    </Style>
</ItemsControl.ItemContainerStyle>
----

* `Canvas.Left/Top` müssen am Container gesetzt werden, nicht im `DataTemplate`, weil der Container das direkte Kind des Canvas ist.

=== ListView mit Spalten

[source,xml]
----
<ListView ItemsSource="{Binding Items}">
    <ListView.View>
        <GridView>
            <GridViewColumn Header="Name" DisplayMemberBinding="{Binding Name}" Width="120"/>
            <GridViewColumn Header="Wert" DisplayMemberBinding="{Binding Value}" Width="80"/>
        </GridView>
    </ListView.View>
</ListView>
----

* Tabellenartige Liste mit Überschriften. Jede Spalte bindet an eine Property.

== Styles und Trigger

=== Impliziter und benannter Style

[source,xml]
----
<Window.Resources>
    <Style TargetType="Button">
        <Setter Property="Margin" Value="2"/>
    </Style>

    <Style x:Key="AccentButton" TargetType="Button" BasedOn="{StaticResource {x:Type Button}}">
        <Setter Property="Background" Value="SteelBlue"/>
    </Style>
</Window.Resources>

<Button Style="{StaticResource AccentButton}" Content="OK"/>
----

* Ohne `x:Key` gilt der Style automatisch für alle Elemente dieses Typs (implizit).
* Mit `x:Key` gilt er nur über `Style="{StaticResource Key}"`.
* Ein benannter Style ersetzt den impliziten. `BasedOn="{StaticResource {x:Type Button}}"` übernimmt den impliziten trotzdem.
* Gültigkeitsbereich: `Application.Resources` (ganze App) > `Window.Resources` > lokale `Resources`. Der nächstgelegene gewinnt.

=== Property-Trigger

[source,xml]
----
<Style.Triggers>
    <Trigger Property="IsFocused" Value="True">
        <Setter Property="Background" Value="LightYellow"/>
    </Trigger>
</Style.Triggers>
----

* Reagiert auf eine Property des Controls selbst (`IsFocused`, `IsEnabled`, `IsMouseOver` ...).
* Beim `Button`-Hintergrund wirkt `IsMouseOver` nicht sichtbar, weil das Standard-Template ihn überschreibt.

=== DataTrigger

[source,xml]
----
<Style TargetType="TextBlock">
    <Setter Property="Foreground" Value="Black"/>
    <Style.Triggers>
        <DataTrigger Binding="{Binding IsActive}" Value="True">
            <Setter Property="Foreground" Value="Green"/>
        </DataTrigger>
    </Style.Triggers>
</Style>
----

* Reagiert auf Daten aus dem ViewModel bzw. dem Element.
* Vergleicht nur auf Gleichheit (kein `>`/`<`). Für Bereiche eine `bool`-Property im ViewModel ergänzen.
* Treffen mehrere Trigger zu, gewinnt der letzte.
* Den Standardwert als `Setter` im Style setzen, nicht direkt am Element. Ein lokales Attribut schlägt jeden Trigger.

=== MultiDataTrigger

[source,xml]
----
<MultiDataTrigger>
    <MultiDataTrigger.Conditions>
        <Condition Binding="{Binding IsActive}" Value="True"/>
        <Condition Binding="{Binding HasError}" Value="False"/>
    </MultiDataTrigger.Conditions>
    <Setter Property="Background" Value="LightGreen"/>
</MultiDataTrigger>
----

* Greift nur, wenn alle Bedingungen erfüllt sind (UND).

=== Ressourcen

[source,xml]
----
<Application.Resources>
    <SolidColorBrush x:Key="AccentBrush" Color="#FF2D7D46"/>
</Application.Resources>

<TextBlock Foreground="{StaticResource AccentBrush}"/>
----

* Einen Wert einmal definieren und überall wiederverwenden.
* `StaticResource` wird einmal beim Laden aufgelöst. `DynamicResource` aktualisiert sich, wenn die Ressource getauscht wird.

== Converter

=== Convert-Methode

[source,csharp]
----
public object Convert(object value, Type targetType, object parameter, CultureInfo culture)
    => value is true ? Visibility.Visible : Visibility.Collapsed;
----

* Teil einer Klasse, die `IValueConverter` implementiert. Wandelt einen ViewModel-Wert in einen UI-Wert um.
* `ConvertBack` wird nur bei TwoWay-Bindings gebraucht, sonst `throw new NotSupportedException()`.

=== Converter verwenden

[source,xml]
----
<Window.Resources>
    <BooleanToVisibilityConverter x:Key="BoolToVis"/>
</Window.Resources>

<TextBlock Visibility="{Binding IsVisible, Converter={StaticResource BoolToVis}}"/>
----

* `BooleanToVisibilityConverter` ist in WPF schon enthalten. Eigene Converter werden genauso als Ressource angelegt.
* Oft ist ein DataTrigger oder eine zusätzliche Property einfacher als ein Converter.

== Controls

[source,xml]
----
<TextBox Text="{Binding Input}" IsReadOnly="True" HorizontalContentAlignment="Right"/>
<CheckBox Content="Aktiv" IsChecked="{Binding IsActive}"/>
<RadioButton GroupName="Mode" Content="A" IsChecked="{Binding IsModeA}"/>
<ComboBox ItemsSource="{Binding Options}" SelectedItem="{Binding SelectedOption}"/>
<Slider Minimum="0" Maximum="100" Value="{Binding Level}"/>
<ProgressBar Minimum="0" Maximum="100" Value="{Binding Progress}" Height="10"/>
<Button Content="OK" IsDefault="True"/>
<Button Content="Abbrechen" IsCancel="True"/>
----

* `TextBox` mit `IsReadOnly` dient als Anzeige.
* `TextBlock` (Property `Text`) ist schlanker als `Label` (Property `Content`, unterstützt Zugriffstasten mit `_`).
* `IsChecked` ist `bool?`, lässt sich aber an `bool` binden.
* `IsDefault`: Enter löst den Button aus. `IsCancel`: Esc löst ihn aus.

== Timer und Dialoge

=== DispatcherTimer

[source,csharp]
----
var timer = new DispatcherTimer { Interval = TimeSpan.FromSeconds(1) };
timer.Tick += (s, e) => Seconds++;
timer.Start();   // timer.Stop(); timer.IsEnabled
----

* Feuert im UI-Thread, daher dürfen Properties und `ObservableCollection` direkt geändert werden.
* `System.Timers.Timer` läuft in einem anderen Thread und stürzt ab, wenn er das UI berührt.

=== Neues Fenster öffnen

[source,csharp]
----
var window = new OtherWindow { Owner = this };
bool? result = window.ShowDialog();   // modal; Show() = nicht modal
----

* `ShowDialog()` blockiert bis zum Schließen und liefert `DialogResult`.

=== MessageBox

[source,csharp]
----
var answer = MessageBox.Show("Wirklich löschen?", "Bestätigen",
                             MessageBoxButton.YesNo, MessageBoxImage.Question);
if (answer == MessageBoxResult.Yes) { ... }
----

=== Event-Handler im Code-Behind

[source,xml]
----
<Button x:Name="okButton" Content="OK" Click="OkButton_Click"/>
----

[source,csharp]
----
private void OkButton_Click(object sender, RoutedEventArgs e) { ... }
----

* Klassischer Weg ohne MVVM. `x:Name` macht das Control im Code-Behind als Feld verfügbar.

== Async / Await

=== Grundregel

[source,csharp]
----
await Task.Delay(500);        // gut: UI bleibt bedienbar
Thread.Sleep(500);            // schlecht: Fenster friert ein
----

* `await` gibt den UI-Thread frei, solange gewartet wird. Danach läuft der Code automatisch im UI-Thread weiter.
* Darum dürfen nach einem `await` Properties und `ObservableCollection` direkt geändert werden.

=== Async-Command

[source,csharp]
----
LoadCommand = new DelegateCommand(async () => await LoadAsync());

private async Task LoadAsync()
{
    var data = await _service.GetDataAsync();
    Items.Clear();
    foreach (var item in data) Items.Add(item);
}
----

* Die Logik in eine `async Task`-Methode legen, der Command ruft sie nur auf.
* Weil `DelegateCommand` eine `Action` erwartet, wird das Lambda zu `async void`. Eine Exception darin bringt die App zum Absturz, daher abfangen (siehe unten).

=== Async-Event-Handler

[source,csharp]
----
private async void LoadButton_Click(object sender, RoutedEventArgs e)
{
    await LoadAsync();
}
----

* `async void` ist *nur* bei Event-Handlern erlaubt. Alle anderen async-Methoden geben `Task` oder `Task<T>` zurück.

=== Rechenintensive Arbeit auslagern

[source,csharp]
----
int result = await Task.Run(() => HeavyCalculation(input));
Result = result;   // wieder im UI-Thread
----

* `Task.Run` führt CPU-lastigen Code in einem Hintergrund-Thread aus.
* Innerhalb von `Task.Run` keine UI-Elemente oder gebundenen Collections ändern. Das Ergebnis erst nach dem `await` zuweisen.
* I/O-Methoden (`HttpClient`, `File.ReadAllTextAsync`) sind schon asynchron und brauchen kein `Task.Run`.

=== Busy-Status und Button sperren

[source,csharp]
----
private bool _isBusy;
public bool IsBusy
{
    get => _isBusy;
    set => SetProperty(ref _isBusy, value);
}

LoadCommand = new DelegateCommand(async () =>
{
    IsBusy = true;
    try { await LoadAsync(); }
    finally
    {
        IsBusy = false;
        CommandManager.InvalidateRequerySuggested();
    }
}, () => !IsBusy);
----

* Verhindert Doppelklicks, solange die Aufgabe läuft.
* `finally` stellt sicher, dass `IsBusy` auch bei einem Fehler zurückgesetzt wird.
* `IsBusy` lässt sich z. B. an `ProgressBar IsIndeterminate="{Binding IsBusy}"` binden.

=== Fehler abfangen

[source,csharp]
----
try
{
    await LoadAsync();
}
catch (Exception ex)
{
    ErrorMessage = ex.Message;
}
----

* Exceptions aus einem `await` landen ganz normal im `catch`.
* In `async void`-Lambdas und Event-Handlern immer `try/catch` verwenden, sonst stürzt die App ab.

=== Fortschritt melden

[source,csharp]
----
var progress = new Progress<int>(p => Progress = p);
await Task.Run(() => DoWork(progress));

private void DoWork(IProgress<int> progress)
{
    for (int i = 0; i <= 100; i++)
    {
        // ... Arbeit ...
        progress.Report(i);
    }
}
----

* `Progress<T>` führt den Callback automatisch im UI-Thread aus. Darum ist kein `Dispatcher` nötig.

=== Abbrechen

[source,csharp]
----
private CancellationTokenSource _cts;

StartCommand  = new DelegateCommand(async () =>
{
    _cts = new CancellationTokenSource();
    try { await RunAsync(_cts.Token); }
    catch (OperationCanceledException) { Status = "Abgebrochen"; }
});
CancelCommand = new DelegateCommand(() => _cts?.Cancel());

private async Task RunAsync(CancellationToken token)
{
    while (true)
    {
        await Task.Delay(200, token);   // wirft bei Abbruch
        Step();
    }
}
----

* `Cancel()` setzt das Token. `Task.Delay(..., token)` und `token.ThrowIfCancellationRequested()` reagieren darauf.
* Ein Abbruch kommt als `OperationCanceledException` an und wird extra abgefangen.

=== Wiederholte Schritte mit Pause (Animation)

[source,csharp]
----
foreach (var step in steps)
{
    Execute(step);
    await Task.Delay(100);
}
----

* Einfache Alternative zum `DispatcherTimer`, wenn Schritte nacheinander sichtbar werden sollen.

=== Beim Start laden

[source,xml]
----
<Window ... Loaded="Window_Loaded">
----

[source,csharp]
----
private async void Window_Loaded(object sender, RoutedEventArgs e)
{
    await ((MainWindowViewModel)DataContext).LoadAsync();
}
----

* Ein Konstruktor kann nicht `await`en. Daher im `Loaded`-Event laden oder einen Command beim Start auslösen.

=== UI aus einem fremden Thread aktualisieren

[source,csharp]
----
Application.Current.Dispatcher.Invoke(() => Status = "Fertig");
await Application.Current.Dispatcher.InvokeAsync(() => Items.Add(item));
----

* Nur nötig, wenn Code ohne `await` in einem anderen Thread läuft (z. B. `System.Timers.Timer`, Callbacks von Bibliotheken).

=== Häufige Async-Fehler

* `.Result` oder `.Wait()` auf einen Task im UI-Thread → Deadlock, das Fenster hängt. Immer `await` verwenden.
* `ConfigureAwait(false)` in ViewModel-Code → danach läuft der Code nicht mehr im UI-Thread, und UI-Updates stürzen ab.
* `async void` außerhalb von Event-Handlern → Exceptions können nicht abgefangen werden.
* Collection in `Task.Run` ändern → `NotSupportedException` („von einem anderen Thread als dem Dispatcher-Thread“).

== Nützliches C#

=== Zahl sicher parsen

[source,csharp]
----
if (double.TryParse(text, NumberStyles.Float, CultureInfo.InvariantCulture, out var value)) { ... }
----

* Wirft keine Exception. Die deutsche Kultur erwartet `,` als Dezimaltrennzeichen, `InvariantCulture` erwartet `.`.

=== Grad in Bogenmaß

[source,csharp]
----
double rad = degrees * Math.PI / 180;
double x = startX + length * Math.Cos(rad);
double y = startY - length * Math.Sin(rad);   // Bildschirm-Y wächst nach unten
----

* `Math.Sin/Cos` rechnen im Bogenmaß. Für Bewegung „nach oben“ Y subtrahieren.

=== Stack

[source,csharp]
----
var stack = new Stack<double>();
stack.Push(3);
double top = stack.Pop();     // entfernt
double peek = stack.Peek();   // nur lesen
----

* LIFO-Speicher, z. B. für Rechner oder Undo-Funktionen.

== Häufige Fehler

* Binding zeigt nichts → im *Output-Fenster* nach `System.Windows.Data Error` suchen (Tippfehler, fehlender DataContext, Feld statt Property).
* UI aktualisiert sich nicht → `OnPropertyChanged` fehlt, oder `List<T>` statt `ObservableCollection<T>`.
* Berechnete Property bleibt alt → im Setter der Quelle `OnPropertyChanged(nameof(...))` ergänzen.
* Button-Zustand bleibt falsch → `CommandManager.InvalidateRequerySuggested()` aufrufen.
* Command im Template feuert nicht → `RelativeSource AncestorType=Window` verwenden.
* Trigger wirkt nicht → Property wurde lokal am Element gesetzt. Standardwert in den Style verschieben.
* Fenster wird beim Start nicht gefunden → `StartupUri`, `x:Class` und Namespace stimmen nicht überein.
